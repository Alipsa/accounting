# Voucher Series Combo Box — Design Spec

**Date:** 2026-07-30

## Context

The voucher editor's series control (`VoucherPanel.seriesField`) is a plain `JTextField`. There is no way to see which voucher series exist for a fiscal year without printing a report, because series aren't a managed list today — `VoucherService.ensureSeries()` (called from `insertVoucher`) silently creates a new series row (named `Serie <code>`) the first time someone types an unrecognized code and saves a voucher. The field is only enabled while composing a brand-new voucher (`seriesField.enabled = currentVoucher == null`); once an existing voucher is loaded it just displays that voucher's series code, read-only.

`VoucherService` already has what's needed to fix this without new service-layer work:
- `listSeries(fiscalYearId)` returns `List<VoucherSeries>` (id, code, name, next running number), ordered by code.
- `ensureSeries(fiscalYearId, seriesCode, seriesName = null)` is already public, validates the code (`normalizeSeriesCode`: uppercased, 1-8 chars, `A-Z0-9`), and is idempotent — calling it with a code that already exists just returns the existing row instead of erroring.
- `VoucherSeries.toString()` already renders `"CODE - Name"`.

## Scope

- `VoucherPanel.groovy`: replace `seriesField` (`JTextField`) with `seriesComboBox` (`JComboBox<VoucherSeries>`, **not editable**) plus a `+` button next to it.
- New `NewVoucherSeriesDialog.groovy`: small modal dialog (code + optional name) that calls `voucherService.ensureSeries(...)`.
- i18n additions for the new button and dialog (`messages.properties` / `messages_sv.properties`).
- Test coverage for the dialog's validation and the panel's combo behavior.

Out of scope: renaming/deleting/editing existing series, reordering series, any change to `VoucherService`'s series schema or `ensureSeries`/`listSeries` themselves, changing how series are stored on `Voucher`/`VoucherLine`.

## Behavior change: no more free-typed codes

Today, typing an unrecognized code into the field and saving silently creates that series. This spec **removes that path**: the combo is locked to existing series, and `+` is the only way to create a new one. This is the actual fix for "invisible series" — every series that ever gets created is now a deliberate, visible action, not a side effect of a typo.

**Empty-state default.** A brand new fiscal year has zero rows in `voucher_series` until the first voucher is ever saved (nothing seeds one today). With the combo locked, an empty list would block the very first voucher. To keep that zero-friction, a default `A` series is seeded — but **only** at the point a new, genuinely editable voucher is being composed, never merely from populating/viewing the combo (see `ensureDefaultSeriesForNewVoucher()` below). Every series *after* that first default one is explicit via `+`.

**Locked periods must not write anything.** The old text field being "enabled" while composing a new voucher in a locked period was harmless, because nothing persisted until `Save` — which is already blocked (`saveButton.enabled = !readOnly`). The `+` button breaks that assumption: it calls `ensureSeries` immediately on click, independent of whether the resulting voucher could ever be saved. Three rules follow, all detailed below: (1) `+` is only enabled when composing a new voucher *and* that voucher's date isn't in a locked period; (2) populating the combo (`refreshSeriesComboBox()`) is a pure read with no side effects — the `A` seed never happens just from opening/browsing a fiscal year, locked or not; and (3) that lock check tracks the date actually being composed (`datePicker.date`, live), not a snapshot taken when the blank voucher was first initialized — otherwise changing the date afterward (typing a locked date, or restoring a draft whose date differs from the picker's value at initialization) would leave `+` enabled against a stale, already-wrong lock decision.

## Components

### `VoucherPanel.groovy`

- Field: `private final JComboBox<VoucherSeries> seriesComboBox = new JComboBox<>()`, `seriesComboBox.editable = false`.
- New button `newSeriesButton`, built with the existing `navigationButton('+', 'voucherPanel.button.newSeries') { createNewSeries() }` helper, placed immediately after the combo in `buildHeaderBar()`.
- New `private boolean isNewVoucherPeriodLocked()`: extracts the lock check `applyReadOnlyState()` already performs for the "composing a new voucher" case, **with one correction**: the date tested is `datePicker.date ?: defaultDate()`, not `defaultDate()` alone. The original inline check used `defaultDate()` (a computed suggestion — `voucherService.latestVoucherDate(...) ?: fy.startDate`) even though `applyReadOnlyState()` runs after `datePicker.date` has already been set to that same value in `showEmptyVoucher()`/`showVoucher()` — so at every point the *old* text-field code checked it, `defaultDate()` and `datePicker.date` happened to agree. That stops being true the moment the date is edited afterward (live typing, or `applyDraft()` overwriting `datePicker.date` with the draft's real accounting date *after* `showBlankVoucher()` already ran `applyReadOnlyState()` against `defaultDate()`). Checking `datePicker.date` directly is what makes the lock check track whatever date is actually about to be saved, in every case — this is a real fix, not just new-code hygiene, since `applyReadOnlyState()` itself reuses this helper (see below) and today's `saveButton` enablement has the same latent staleness. `accountingPeriodService.isDateLocked(activeCompanyManager.companyId, date)` is still wrapped in the same try/catch-as-locked/`true`, same log message. Returns `true` (fail closed) if there's no active fiscal year.
- New `datePicker` listener, registered once during `buildUi()` (a plain local wiring like `descriptionField.addActionListener{...}`/`jumpField.addActionListener{...}` already get — not through the `ListenerLifecycle` trait, which is reserved for external singleton subscriptions (`I18n`, `ActiveCompanyManager`) that must be unregistered to avoid leaking this panel; `datePicker` is a child component owned by and disposed with this panel, so no separate teardown is needed): `datePicker.addListener { LocalDate date -> applyReadOnlyState() }`. `DatePicker.setDate()` only notifies listeners when the value actually changes, so this fires for live user edits *and* every programmatic `datePicker.date = ...` assignment (`showVoucher`, `showEmptyVoucher`, `applyDraft`) that changes the value — which is exactly what closes the gap: `applyDraft()`'s `datePicker.date = voucherDraft.accountingDate` (set *after* `showBlankVoucher()` already computed lock state for a different date) now correctly re-triggers `applyReadOnlyState()` for the draft's real date, recomputing both `readOnly`/`saveButton.enabled` and `newSeriesButton.enabled` against it. Because this makes `applyReadOnlyState()` reentrant on every date edit (not just at voucher-load time as before), the `datePicker.enabled` rule inside it needs its own carve-out — see below — otherwise picking a locked date would disable the date picker itself and trap the user in it.
- New `private void refreshSeriesComboBox(String preferredCode = null)` — **pure read, no writes, safe to call from any context including a locked/closed fiscal year:**
  1. Resolve `FiscalYear fy = activeCompanyManager.fiscalYear`; if null, clear the combo model and return.
  2. `List<VoucherSeries> series = voucherService.listSeries(fy.id)` (may be empty — that's fine here; seeding is a separate, gated step, see `ensureDefaultSeriesForNewVoucher()` below).
  3. Rebuild the combo model from `series`, which may leave it empty.
  4. Select `preferredCode` if given and present in the list; else keep the previous selection if still present; else select the first item if any exist.
  - Called as the **first statement** of `reloadVoucherList()`, before `cancelBalancePreload()` and, critically, before any `showBlankVoucher()`/`showVoucher()`/`navigation.select(...)` call in that method. `reloadVoucherList()`'s existing body calls one of those `show*` methods as its last action in every branch (not after some later "end" of the method) — placing the refresh anywhere but first would let `showEmptyVoucher()`/`showVoucher()` run against the *previous* fiscal year's still-loaded combo items when switching fiscal years, which is wrong in two ways: `ensureDefaultSeriesForNewVoucher()` would see non-zero `itemCount` (the old year's series) and decline to seed `A` for a genuinely empty new year, and `showEmptyVoucher()`/`showVoucher()` would preview/select a stale series that a moment later gets wiped out when the combo is (too late) rebuilt. Calling it first means `reloadVoucherList()` covers construction, fiscal-year switch, and company switch (it already runs on all three via the existing `propertyChange` listener) with the combo always reflecting the *target* fiscal year before anything reads it. Called again after a successful `createNewSeries()` (passing the new code as `preferredCode`).
- New `private void ensureDefaultSeriesForNewVoucher()` — the only place that seeds the default `A` series, and the only place besides `createNewSeries()` that writes to `voucher_series`:
  1. If `activeCompanyManager.fiscalYear == null` or `seriesComboBox.itemCount > 0`, return (nothing to do — either no context, or series already exist so there's nothing to default).
  2. If `isNewVoucherPeriodLocked()`, return **without seeding** — an empty combo in a locked period is fine: `Save` is already disabled by `readOnly`, so there is no new voucher this could mislead.
  3. Otherwise: `voucherService.ensureSeries(fy.id, 'A')`, then `refreshSeriesComboBox('A')`.
  - Called from `showEmptyVoucher()` **after** `datePicker.date` has been reset to `defaultDate()` for this new blank voucher, but before anything reads the combo's selection (see below). Ordering matters here for the same reason as finding 4: `showEmptyVoucher()` currently resets `datePicker.date = defaultDate()` partway through the method (after the old `previewNextVoucherNumber('A')` call, before `applyReadOnlyState()` at the end); this design moves that assignment earlier, to immediately after `currentVoucher = null`/`pendingReceiptAttachmentPath = null`/`readOnly = false`, so `isNewVoucherPeriodLocked()` (called via `ensureDefaultSeriesForNewVoucher()` right after) reads the *correct* date for this new voucher rather than whatever date was left over from the previously displayed voucher/draft. The move also means the new `datePicker` listener fires `applyReadOnlyState()` once, early, in addition to the explicit call still at the end of `showEmptyVoucher()` — redundant but harmless (idempotent).
- New `private void createNewSeries()`:
  - Guards defensively on `activeCompanyManager.fiscalYear != null && !isNewVoucherPeriodLocked()` before showing the dialog — the button's own `enabled` state (below) already prevents this call in the normal UI flow, but this is the write path, so it re-checks rather than trusting only the button state (e.g. a future caller invoking this method directly, or any UI enablement bug, must not be able to bypass the lock). If the guard fails, show an error via the existing `showError(...)` convention and return without opening the dialog.
  - Shows `NewVoucherSeriesDialog`, which returns the created/matched `VoucherSeries` or `null` if cancelled.
  - On success: `refreshSeriesComboBox(result.seriesCode)`.
- Read/write sites switch from `seriesField.text` to the combo's selection:
  - New private helper `VoucherSeries findComboSeries(String code)`: linear scan of the combo's current items for `seriesCode == code`, returns the match or `null`. Single lookup used by both the fail-soft `selectSeriesCode` (below) and the strict `applyDraft()` validation (below) — one implementation of "does this code exist in the currently-loaded fiscal year's series."
  - `showVoucher(v)`: select via `selectSeriesCode(String code)` = `findComboSeries(code)?.with { seriesComboBox.selectedItem = it }` — falls back to leaving the current selection if no match (shouldn't happen, since a voucher's series always belongs to its own fiscal year, but fail-soft rather than throw: this is read-only display of an already-saved, already-immutable voucher, not a write path).
  - `showEmptyVoucher()`: call `ensureDefaultSeriesForNewVoucher()` **first**. Then, instead of hardcoding `'A'` anywhere (the bug being fixed here — the old code called `previewNextVoucherNumber('A')` unconditionally, regardless of what was actually selected), read the combo's actual state: `VoucherSeries selected = seriesComboBox.selectedItem as VoucherSeries`. If non-null, `nextNumber = previewNextVoucherNumber(selected.seriesCode)`; if null (fiscal year has no series and the period is locked, so `ensureDefaultSeriesForNewVoucher()` correctly declined to seed), `nextNumber` is a blank/placeholder string — there is nothing to preview because nothing can be saved. This guarantees the displayed number always matches whatever series will actually be used if `Save` is (or becomes) available.
  - `duplicateVoucher()`: `selectSeriesCode(source.seriesCode ?: 'A')` — unaffected by this fix, `source.seriesCode` is always a real, already-persisted series from an existing voucher, never a guess.
  - `snapshotDraft()`: reads via `(seriesComboBox.selectedItem as VoucherSeries)?.seriesCode` — the draft's `seriesCode` stays a plain `String`, unchanged on the `VoucherDraftMapper` boundary. Always a real, currently-selected series, since the combo is locked to real items.
  - **`applyDraft(voucherDraft)` — strict, not fail-soft, because this is the one place an *external, unvalidated* series code enters the panel.** `VoucherDraftMapper.fromDraft()` reads `series_code` from an arbitrary `Map<String, Object>` with no validation beyond a blank/`'A'` default — and that map can come straight from an MCP tool call (`set_active_voucher_draft`, wired through `VoucherDraftEditorAccess.setVoucherDraft` → `this::applyDraft` as the `draftConsumer`, see `VoucherPanel` constructor). Silently falling back to whatever the combo happens to have selected (the `A` default from `showBlankVoucher()`, or a leftover selection) would let a later `Save` post the voucher into a *different* series than the caller asked for, with no error — exactly the kind of silent substitution `CLAUDE.md`'s data-integrity rules exist to prevent for saved data, and no better for an about-to-be-saved draft. Fix: validate **before** mutating any panel state (not after — mutating first and throwing partway through would leave the panel in an inconsistent half-applied state):
    1. `VoucherSeries requestedSeries = findComboSeries(voucherDraft.seriesCode)`.
    2. If `null`: `throw new IllegalArgumentException("Unknown voucher series '${voucherDraft.seriesCode}' for the current fiscal year. Create it first or choose an existing series.")` and do nothing else — the panel's current display is untouched.
    3. Otherwise, proceed exactly as before (`showBlankVoucher()`, `datePicker.date = voucherDraft.accountingDate`, description, lines, attachment), except the series is applied as `seriesComboBox.selectedItem = requestedSeries` directly (already resolved and known-valid) rather than going through `selectSeriesCode`.
    - This message is a plain string, not run through `I18n` — consistent with `VoucherService`'s own validation exceptions (e.g. `normalizeSeriesCode`'s `IllegalArgumentException`), which are developer/API-facing rather than routed through Swing dialog i18n.
    - **MCP path:** `this::applyDraft` is used directly as `VoucherDraftEditorAccess`'s `draftConsumer`, invoked inside `SwingThreading.runOnEdt` — which already exists specifically to unwrap `InvocationTargetException` and rethrow the original `IllegalArgumentException` ("*preserving validation errors*", per its own doc comment). No changes needed there: the exception propagates straight back to the MCP tool caller as a real error, telling the assistant the series doesn't exist instead of silently switching it.
    - **Internal path:** `restoreNavigationDraft()` (navigation's own remembered-draft restore, entirely internal — the draft it passes was populated by `snapshotDraft()` moments earlier in the same fiscal year, so its `seriesCode` should always resolve) wraps its `applyDraft(draft)` call in try/catch for `IllegalArgumentException`, falling back to `showEmptyVoucher()` on the (should-never-happen) case where it doesn't — an uncaught exception from a Swing navigation callback is a worse failure mode than silently starting a blank voucher, and this path never had untrusted input to begin with. **Note for testing this path:** since this design adds no way to remove or rename a series (out of scope), a series that was validly selected when `snapshotDraft()` ran can never actually become invalid by the time `restoreNavigationDraft()` reads it back — there is no real user action that reproduces this case. Exercising the fallback therefore requires a deliberately-constructed invalid `VoucherDraftMapper.VoucherDraft` injected directly (see the new `@PackageScope` seam below), not an attempt to make a real series "disappear."
  - New `@PackageScope void rememberDraftForTest(VoucherDraftMapper.VoucherDraft draft)`: thin wrapper around `navigation.rememberDraft(draft)`, added purely so `VoucherPanelNavigationTest` (same package) can seed an intentionally-invalid remembered draft to test the `restoreNavigationDraft()` fallback above — the only such case in this design, since it can't otherwise arise. Follows the same pattern as this class's existing `@PackageScope` test seams (`cursorMover`, `dateFocusRequester`, `lineTableModel`).
  - `VoucherEditorActions` construction (`seriesSupplier`): `{ (seriesComboBox.selectedItem as VoucherSeries)?.seriesCode ?: 'A' }` — `VoucherEditorActions`'s own signature (`Supplier<String>`) is unchanged. The `?: 'A'` fallback is now unreachable in practice for a savable voucher (by the time `Save` is enabled, `ensureDefaultSeriesForNewVoucher()` has guaranteed a selection), but kept as a defensive default matching the supplier's existing contract.
- `applyReadOnlyState()`:
  - `seriesComboBox.enabled = currentVoucher == null` (unchanged rule — merely *selecting* among already-existing series doesn't write anything, so it doesn't need the lock check; the write only happens at `Save`, already gated by `saveButton.enabled = !readOnly`).
  - `newSeriesButton.enabled = currentVoucher == null && !readOnly` — this is the fix for the "+" button: creating a series is an immediate write, so it must respect the same lock check as `Save`, not just "is this a new voucher".
  - **`datePicker.enabled` changes from the existing `!readOnly` to `currentVoucher == null || !readOnly`.** This is required *because of* the new `datePicker` listener above: today `applyReadOnlyState()` only ever runs at voucher-load time, so `datePicker.enabled = !readOnly` was harmless — the date was already set to a known-open `defaultDate()` by the time it ran. Once the listener re-runs `applyReadOnlyState()` on every date change, the plain `!readOnly` rule becomes a trap: the moment a user composing a new voucher types/picks a date that falls in a locked period, `readOnly` flips to `true` and `DatePicker.setEnabled(false)` disables *both* the text field and the calendar button and closes the popup (per `DatePicker.setEnabled()`) — leaving no UI path back to an open date. The corrected rule keeps the date picker enabled for the entire duration of composing a new voucher (`currentVoucher == null`), regardless of whether the currently-entered date happens to be locked, so the user can always correct it themselves; `Save`, line editing, and `+` still correctly disable while the date is locked, and the date picker itself disables again once an existing voucher is loaded (`currentVoucher != null`, where `readOnly` is unconditionally `true`, so the expression still evaluates to `false` — no change to that case).
- Bonus (small, low-risk UX win enabled by the structured model): add an item listener on `seriesComboBox` that updates `voucherNumberLabel`/`jumpField` live via the existing `previewNextVoucherNumber(seriesCode)`. Must guard on `currentVoucher == null` (only meaningful while composing a new voucher) **and** not fire during programmatic selection from `showVoucher`/`duplicateVoucher`/`applyDraft`/`refreshSeriesComboBox` — those already set the correct label themselves (e.g. `showVoucher` sets it from the loaded voucher's real number, not a preview) and must not have it overwritten. The existing codebase convention for this is a reentrancy guard flag set around programmatic `setSelectedItem` calls; the implementation plan should follow it.

### `NewVoucherSeriesDialog.groovy` (new file)

- Modal `JDialog`, sized/styled like existing small dialogs (e.g. `PeriodLockDialog`).
- Fields: series code (`JTextField`, required), series name (`JTextField`, optional).
- OK button: trims/uppercases the code client-side and checks it against `1-8 chars, A-Z0-9` before calling the service (same rule as `VoucherService.normalizeSeriesCode`, duplicated client-side only for immediate inline feedback — the service call remains the source of truth). On a validation failure, shows an inline error label rather than closing.
- Calls `voucherService.ensureSeries(fiscalYearId, code, name?.trim() ?: null)`. Any `IllegalArgumentException` from the service (defensive backstop) is shown the same way.
- If the entered code already exists, `ensureSeries` just returns that existing row — the dialog treats this as success (no special-cased "already exists" error), closes, and the panel selects it.
- Cancel / window-close returns `null`.
- Constructor takes the owner frame, `VoucherService`, and `fiscalYearId`; a static `static VoucherSeries showDialog(Frame owner, VoucherService voucherService, long fiscalYearId)` mirrors the calling convention other dialogs in this package use.

## Testing

- New unit test `NewVoucherSeriesDialogTest` (or equivalent headless-safe test) covering code validation (rejects empty/too-long/invalid-character codes) and the "existing code selects existing series" path, using a real `VoucherService` against a temp DB (matching how `VoucherPanelNavigationTest` is set up).
- Extend `VoucherPanelNavigationTest` (integration):
  - A fresh, open fiscal year with no vouchers yet shows the combo pre-populated with a single seeded `A` series, and the voucher-number preview reads `A-1`.
  - Creating a second series via `createNewSeries()`/the dialog makes it appear in the combo and become selected.
  - Switching fiscal year repopulates the combo with that year's series.
  - Combo and `+` button are disabled once an existing voucher is loaded, matching the current `seriesField` behavior.
  - **Locked-period regression (finding 1):** a fiscal year/period locked via `AccountingPeriodService` with zero existing series — merely opening/viewing it must not create a `voucher_series` row (assert `listSeries()` still returns empty after `reloadVoucherList()`/`showEmptyVoucher()`), and `newSeriesButton.enabled` must be `false`.
  - **Non-`A` default series regression (finding 2):** a fiscal year whose only series is `B` (seeded directly via `ensureSeries(fy.id, 'B')` in test setup, simulating an imported/legacy year) — `showEmptyVoucher()` must select `B` in the combo *and* the voucher-number preview must read `B-<next>`, never `A-*`. Then actually saving must produce a `B-*` voucher number, confirming the label and the save path agree.
  - **Stale-combo-on-fiscal-year-switch regression (finding 3):** with two fiscal years open in the same company/panel — year 1 has series `B` selected (no `A`), year 2 is brand new with zero series and open (not locked). Switching the active fiscal year from year 1 to year 2 (via `activeCompanyManager`, triggering `reloadVoucherList()`) must result in year 2's combo showing the freshly-seeded `A` (not a leftover `B` from year 1, and not an empty/unselected combo), and the voucher-number preview must read `A-1`. This specifically catches `refreshSeriesComboBox()` running after `showEmptyVoucher()` instead of before.
  - **Date-changed-after-init regression (finding 4):** start a new blank voucher in an open period (`+` enabled), then set `datePicker.date` to a date in a locked period (via `datePicker.setDate(...)`, simulating the user typing/picking it) — `newSeriesButton.enabled` must become `false` without any other action. Separately, restore a draft (`applyDraft`) whose `accountingDate` falls in a locked period, from a starting state where the panel's `defaultDate()` would *not* be locked — `newSeriesButton.enabled` must be `false` after `applyDraft()` returns, not just after some later interaction. Also directly call `createNewSeries()` while in this locked state (bypassing the UI's own enablement, simulating an enablement bug) and assert it shows an error and does not create a `voucher_series` row.
  - **Date-picker-stays-usable regression (finding 5):** continuing the scenario above (new voucher, date set to a locked period) — `datePicker.enabled` must remain `true` throughout (never trapped), while `saveButton.enabled`, `newSeriesButton.enabled`, and `lineTableModel.editable` are all `false`. Then set `datePicker.date` back to an open date — `saveButton`/`newSeriesButton`/`lineTableModel.editable` must all become `true` again, without needing to restart the form (e.g. via "New").
  - **Unknown-series-in-draft regression (finding 6):** call `mcpVoucherDraftAccess.setVoucherDraft(draft)` (exercising the real MCP path) with a `series_code` that doesn't exist for the active fiscal year — assert it throws (surfacing as the caller sees it, i.e. after `SwingThreading.runOnEdt`'s unwrapping) and that the panel's displayed voucher/combo selection is unchanged from before the call (no partial application). Separately, drive the purely-internal path: while the panel `isOnDraft()` (fresh blank voucher, no navigation yet — required for `VoucherNavigation.rememberDraft()` to actually store the value), call the new `rememberDraftForTest(...)` seam with a hand-built `VoucherDraftMapper.VoucherDraft` whose `seriesCode` is a code that was never created (e.g. `'ZZZZZZZZ'`) — not a real series that got superseded, since nothing in this design can make an already-created series disappear. Then drive navigation forward through its real, unmodified path (e.g. `doClick()` on the next/prev buttons past the end of the voucher list, the only caller of `restoreNavigationDraft()`) and assert it falls back to a blank voucher rather than propagating the exception out of the navigation callback.
